## 2. Mục tiêu project

Xây dựng desktop pet app cực nhẹ cho Windows 11:

- runtime chính bằng Go/Win32;
- pet có animation mượt;
- hỗ trợ nhiều pet độc lập;
- mỗi pet có name, folder, kho animation riêng;
- có thể chạy một pet, nhiều pet, hoặc nhiều instance cùng pet;
- pet có thể click, right-click, drag;
- drag/click có thể đổi biểu cảm như khóc, giận, happy;
- sau này có thể nhúng vào app khác như plugin/host module;
- sau này có thể tích hợp TTS, vision model, OpenAI completion, float chat, hiệu ứng nốt nhạc, v.v.


## 4. Sprite/animation contract

Mỗi animation nên là một file riêng:

```text
idle.png
walk.png
run.png
happy.png
cry.png
angry.png
wave.png
sleepy.png
```

Mỗi file là horizontal strip:

```text
frame_count * frame_width  x  frame_height
```

Hiện frame chuẩn thường là:

```text
256x256 mỗi frame
5 frame mỗi animation
```

Ví dụ:

```text
walk.png = 1280x256 nếu 5 frame
```

Không nên để `walk_left.png`, `walk_right.png` làm act runtime tự chọn lung tung. Runtime nên dùng:

```text
walk.png
run.png
```

và tự flip theo hướng di chuyển dựa trên metadata `native_facing`.

`act_blacklist` nên có các act không được random chọn sai như:

```text
walk_left
walk_right
run_left
run_right
```

## 8. Bug history quan trọng

### 8.1 Sprite bị cắt lỗi/rỗ mặt

Lỗi cũ: tool detect foreground bằng threshold màu nền trắng/checkerboard, dẫn đến pixel sáng trong mặt/da/highlight bị hiểu nhầm là background và bị xóa.

Fix hiện tại trong Python tool:

- không threshold toàn ảnh;
- dùng flood-fill từ viền ngoài;
- chỉ xóa pixel giống nền và connected với border;
- không khoét lỗ bên trong nhân vật.

### 8.2 Walk/run sai hướng

Lỗi cũ:

- pet đang move trái nhưng animation walk_right;
- hoặc move phải nhưng animation chân/hướng sai;
- hoặc action emotional như cry đang bị dùng trong lúc di chuyển.

Hướng xử lý:

- locomotion chỉ dùng `walk`/`run`;
- runtime tự flip theo facing;
- emotion/reaction không dùng làm locomotion;
- `act_blacklist` loại các file trái/phải explicit hoặc act không nên random locomotion.

### 8.3 Click đúp làm pet bám mouse

Lỗi cũ: xử lý drag ngay tại `WM_LBUTTONDOWN`, double-click tạo `WM_LBUTTONDBLCLK` xen kẽ, capture state lệch.

Đã đổi sang pending click:

```text
WM_LBUTTONDOWN -> PendingLeft
nếu giữ >180ms hoặc rê >10px -> Drag
WM_LBUTTONUP nếu chưa drag -> click thường
WM_LBUTTONDBLCLK -> cancel pending/drag + trigger left_click
```

### 8.4 3 pet, drag/click gây lag/shutdown

Lỗi cũ: dùng `SetCapture/ReleaseCapture`, nhiều window gây `WM_CAPTURECHANGED` re-entrant, app shutdown/native crash khó bắt panic.

Đã bỏ `SetCapture/ReleaseCapture`.

### 8.5 Chuột phải sau click nhiều pet force close

Bug mới nhất trước reset.

Log user gửi:

```text
2026/05/25 04:01:22.900005 main.go:669: drag begin hwnd=17567282 pet=pet4-3 reason=pending_promoted offset=(40,52) pos=(1600,890)
2026/05/25 04:01:23.407480 main.go:682: drag end hwnd=17567282 pet=pet4-3 reason=left_up pos=(1622,905)
...
2026/05/25 04:01:30.236108 main.go:682: drag end hwnd=1578272 pet=pet4-2 reason=left_up pos=(1586,899)
PS E:\git-project\desktop-pet-lite\go-lite>
```

User mô tả: chạy 3 pet, click mỗi con 1-2 cái rồi chuột phải test là force close.

Audit gần nhất: nghi ngờ lớn nhất là `wndProc` mutate trực tiếp state pet cùng lúc render goroutine cũng mutate/draw. Đây là race native nguy hiểm, nhất là khi `right_click` gọi `TriggerAction()` trực tiếp trong wndProc.

Đã sửa cuối cùng theo hướng event queue:

```text
wndProc không sửa state pet nữa
wndProc chỉ emit InputEvent vào channel
render loop processInputEvents()
render loop mới gọi beginPendingLeft / endDrag / TriggerAction / runHook
```

Files đã chỉnh gần nhất:

```text
go-lite\main.go
```

Quan trọng: bản cuối đã `go test ./... OK`, build lại `pet-lite.exe` nhưng lệnh build stripped `-s -w` bị shell/MCP trục trặc một lần, bản build cuối có size khoảng:

```text
pet-lite.exe = 4,433,408 bytes
LastWriteTime = 2026/05/25 04:08:20
```

Cần agent sau kiểm tra lại compile/build và test runtime thật.

## 9. Cấu trúc input event mới cần kiểm tra

Trong `go-lite/main.go`, đã thêm concept:

```go
type InputEventKind int

const (
    InputLeftDown InputEventKind = iota + 1
    InputLeftUp
    InputLeftDouble
    InputRightDown
    InputCancel
)

type InputEvent struct {
    Kind   InputEventKind
    HWND   uintptr
    X      int32
    Y      int32
    Reason string
}
```

`App` có:

```go
Inputs chan InputEvent
```

`wndProc` nên chỉ làm:

```go
emitInput(InputEvent{...})
return 0
```

`loop()` nên gọi:

```go
a.processInputEvents()
```

trước update/draw.

Mục tiêu: mọi mutation của pet state xảy ra trong render goroutine, không xảy ra trong Win32 wndProc.

Cần agent sau verify lại file thật vì có nhiều lần patch trong session.

## 12. Known risk areas cần audit tiếp

### 12.1 Threading/race

Các object nguy hiểm nếu bị mutate từ nhiều goroutine:

```text
WindowPet.Drag
WindowPet.PendingLeft
WindowPet.DragOffX / DragOffY
Pet.Animation
Pet.Frame
Pet.FrameAccum
Pet.ForcedTill
Pet.X / Pet.Y
```

Luật mới nên là:

```text
wndProc không mutate trực tiếp các field trên
render loop/processInputEvents là nơi duy nhất mutate
```

### 12.2 UpdateLayeredWindow

`drawPet()` gọi Win32 GDI/UpdateLayeredWindow. Cần giữ nó ở một goroutine ổn định. Nếu vẫn native crash, cân nhắc chuyển render/draw về locked OS thread:

```go
runtime.LockOSThread()
```

ở goroutine gọi Win32 UI/message loop, hoặc tổ chức lại để window create/message/draw cùng một OS thread.

Hiện app có `go app.loop()` và `messageLoop()` ở main goroutine. Đây có thể là vấn đề Win32 nghiêm trọng vì một số Win32/GDI/window thao tác nên nằm cùng thread tạo window/message. Nếu crash vẫn tiếp diễn, hướng refactor mạnh:

```text
main goroutine locked OS thread:
- register class
- create windows
- timer/tick update
- process input
- draw
- message pump
```

Hoặc dùng `PeekMessage` trong single-thread game loop thay vì render goroutine riêng.

### 12.3 Right-click action

Right-click hiện có thể trigger animation/hook. Nếu right-click crash, temporarily disable:

```go
p.Pet.TriggerAction("right_click")
a.runHook(a.RightCommand)
```

để phân biệt crash do Win32 message hay do animation/action.

### 12.4 Hook command

`runHook()` chạy PowerShell nếu command không rỗng. Nếu config có right command/click command, nó có thể gây side effect. Trong log startup có:

```text
click_cmd=false right_cmd=false
```

nhưng vẫn nên kiểm tra.
